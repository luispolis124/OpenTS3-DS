# Decompilation Flow — The Sims 3 (DS), ARM9/ARM7

## 0. What has already been verified in this ROM (VS3E, md5 `7cdf32d0…c1`)

All of this comes from `tools/extract_code.py` running on the ROM, and is located in `asm/memory_layout.txt`.

| Item | Value |
|---|---|
| ARM9 | ROM `0x4000`, 0x17C6C0 bytes, **uncompressed**, loaded at `0x02004000`, entry point `0x02004800` |
| Secure Area | First 0x800 bytes of ARM9, **already decrypted** |
| ARM9 in RAM | Static up to `0x0217CAE0`, `.bss` up to `0x022503A0` |
| ARM9 Autoloads | ITCM `0x01FF8000` (0x3AC0 B) and DTCM **`0x02FE0000`** (0x100 B). The DTCM base is from TWL-SDK, not NitroSDK (`0x027E0000`) |
| ARM7 | Loaded at `0x02380000` (Main RAM), 0x2909C bytes; almost all code is in autoloads (`0x037F8000` and `0x02FE0000`) |
| ARM9 Overlays | 3, uncompressed. Overlays 1 and 2 share the address `0x0225EE20` |
| DSi | `ARM9i` (0x2C74 B) encrypted (modcrypt); `ARM7i` (0x471A4 B) in cleartext |
| SDK | Field `sdk_version = 0x05047531` (major 5; probable TWL-SDK, also deduced from the DTCM base) |

The encrypted ARM9i cannot be disassembled without the key/decryption; start with ARM9/ARM7, which run in DS mode.

## 1. Preparing the repository

`.gitignore`:


baserom.nds
*.nds

The contents of `asm/` and the decompiler outputs are derived from the ROM code, which is copyright-protected. The standard in decompilation projects is for each person to run the extraction on their own ROM. If you want the build to check this, in the Makefile:

```make
BASEROM := baserom.nds

asm/layout.json: $(BASEROM) tools/extract_code.py
	python3 tools/extract_code.py $(BASEROM) -o asm --thumb-ranges tools/thumb_ranges.txt

extract: asm/layout.json

2. Extraction and Disassembly
pip install capstone                          # or have arm-none-eabi-objdump in PATH
python tools/extract_code.py baserom.nds      # generates asm/

Without capstone or arm-none-eabi-objdump, the tool falls back to --backend raw (.word). This is workable because Ghidra will do the actual disassembling; the .s files serve as reference and diff bases.
3. Ghidra
3.1 Importing
Language: ARM:LE:32:v5t for ARM9 (ARM946E-S, ARMv5TE) and ARM:LE:32:v4t for ARM7 (ARM7TDMI). One Ghidra project per CPU.
For each import: Format = Raw Binary, Language as above, and in Options set the Base Address of the segment. For ARM9:
| File (asm/bin/) | Base address | Note |
|---|---|---|
| arm9_main.bin | 0x02004800 | Import this first; becomes the main program |
| arm9_secure.bin | 0x02004000 | File → Add To Program; it's data, mark as non-executable |
| arm9_itcm.bin | 0x01FF8000 | Add To Program |
| arm9_dtcm.bin | 0x02FE0000 | Data |
Then, in Window → Memory Map, add an uninitialized block (.bss) at 0x0217CAE0, size 0xD38C0, and 0x20 B / 0xE00 B .bss blocks at the end of ITCM and DTCM respectively (values found in asm/memory_layout.txt).
For ARM7 the idea is the same: arm7_main.bin at 0x02380000, arm7_wram.bin at 0x037F8000, and arm7_autoload1.bin at 0x02FE0000.
Overlays: Since overlays 1 and 2 overlap, import each overlay (bin/ov9_NNN.bin) as an Overlay block (Memory Map → Add Block → check Overlay) at the address specified in memory_layout.txt. Ghidra creates a separate address space per block, and calls coming from static code need to be resolved manually (see 3.4).
3.2 Symbols and Entry Point
 * Run ImportSymbolsScript.py (comes with Ghidra) with asm/symbols/arm9.sym. This names _start, ModuleParams, the autoload list, and the start of each segment.
 * Disassemble starting from _start (D at 0x02004800) and run automatic analysis.
 * Enable Decompiler Parameter ID. Keep Aggressive Instruction Finder disabled initially: in mixed ARM/Thumb binaries, it generates too many false positives.
3.3 ARM × Thumb
Ghidra decides the mode via the TMode context register. It follows BX/BLX automatically, but functions called only via pointers need assistance: at the entry point, Set Register Values → TMode = 1, then press D. When a region becomes corrupted (code turning into garbage), it is almost always a wrong mode issue.
As you mark Thumb functions, export thumb_ranges.txt (item 5) and run extract_code.py again to keep the .s files synchronized.
3.4 Identifying SDK vs. Game Code
Much of the ARM9 binary is SDK library code (OS, MI, FS, GX, SND…), not game logic. Identify it first, as it removes thousands of functions from view and names the ones that remain:
 * Search for assert/SDK version strings in .data (Search → For Strings). They usually point to modules and compiler versions.
 * Decompilation projects of other DS games publish SDK function names of the same family; compare byte patterns and function order to reuse names.
 * Overlay functions: find the loader (function that reads the y9 table and calls FS), note the address, and create manual references from static callers to the correct overlay.
3.5 Structures
When you discover the size of a struct (loop stride, allocator argument), create it in the Data Type Manager and apply it to parameters (Retype Variable). Then reflect it in include/entity.h and lock it down with STATIC_ASSERT(offsetof(...)).
4. radare2 (alternative)
r2 -a arm -b 32 -m 0x02004800 asm/bin/arm9_main.bin -i asm/arm9.r2
> aaa          # analysis
> afl          # function list
> pdf @ fcn.XXXX
> ahb 16 @ 0xADDRESS   # force Thumb starting from an address

With the r2ghidra plugin installed, pdg @ fcn.XXXX provides pseudo-C. The generated r2 script already opens extra segments (ITCM) and creates flags for symbols. Run from the repository root because paths are relative.
5. Exporting and Transforming into C Modules
 * In Ghidra, run tools/ghidra_export_functions.py (Script Manager, or via analyzeHeadless … -postScript). It generates:
   * functions/ADDRESS_name.c: pseudo-C for each function;
   * index.csv: address, name, size, mode (arm/thumb), and status;
   * thumb_ranges.txt: feeds back into extract_code.py.
 * Group functions into modules based on their purpose and address: contiguous functions usually come from the same original .c source file. One module at a time, starting from leaf functions (no calls) and working your way up.
 * Clean up the pseudo-C manually: real types, names, switch statements instead of if cascades, structures instead of *(int*)(p+0x14). Ghidra's pseudo-C does not compile out-of-the-box nor does it produce matching assembly; it is just a draft.
 * For matching decompilation (C code that compiles down to the exact same bytes), you need the original compiler. Discovering which one (likely Metrowerks CodeWarrior for ARM, but confirm) and its flags (-O4,p, -proc arm946e, etc.) is the hardest part; without it, the result is a non-matching decompilation, which is still useful. Test function by function on decomp.me and compare via assembly diff (objdiff/asm-differ).
 * Register each completed function in the .sym file (real name) and re-import it into Ghidra so callers appear with proper names.
There is also ds-decomp (dsd), a tool built specifically for this type of project: it splits the ROM into modules using a configuration, generates linker scripts, and produces "delinked" objects. It is worth evaluating for the build skeleton; check its current documentation, as command flows change between versions.
6. Suggested Order
 * crt0 in assembly (_start → autoload copy → zero .bss → main). It is short, acts as a pipeline test, and validates the constants in memory_map.h.
 * SDK library (OS/MI/FS), identifying and naming.
 * Overlay loader.
 * Main loop and entity dispatch table (to confirm entity.h).
 * ARM7 (smaller, great for practicing the complete workflow).
7. What has not been tested
extract_code.py was executed on a real ROM using raw backends; the capstone and objdump backends, ghidra_export_functions.py, and arm9.r2 could not be exercised in the environment where they were written (no capstone, no arm-none-eabi-objdump, no Ghidra or radare2 installed). Chunking and parsing logic was validated with simulated substitutes, but the first real use of each may require minor flag/API adjustments.
